# DDS転送・受信キューの切り分け（2026年11月6日）

## 結論

標準Fast DDSの共有メモリセグメントが画像サイズに対して小さいことが、今回の損失の主因と強く考えられる。受信キューを1枚から100枚へ増やしても同じ画像が欠け、共有メモリを64 MiBへ増やすとBest EffortのDDS損失通知と長い受信空白が解消した。画像処理・JPEG変換・中継は追加していない。

## 同時購読による比較

同じ `/image_raw` に対し、同じプロセスで3つの購読を60秒間実行。コールバックは到着時刻と画像ヘッダー時刻の記録だけ。rqtも接続したまま。画像は保存していない。

| 条件 | 受信枚数 | fps | DDS損失通知 | 最大受信間隔 | 0.5秒超の空白 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 標準SHM・Best Effort・深さ1 | 733 | 12.26 | 1049 | 4028 ms | 23 |
| 標準SHM・Best Effort・深さ100 | 733 | 12.26 | 1049 | 4028 ms | 23 |
| 標準SHM・Reliable・深さ100 | 1784 | 29.76 | 0 | 52.3 ms | 0 |
| SHM 64 MiB・Best Effort・深さ1 | 1627 | 27.12 | 0 | 53.1 ms | 0 |
| SHM 64 MiB・Best Effort・深さ100 | 1626 | 27.12 | 0 | 53.2 ms | 0 |
| SHM 64 MiB・Reliable・深さ100 | 1627 | 27.14 | 0 | 56.0 ms | 0 |

標準SHMのBest Effort深さ1・100が受信したヘッダー時刻の集合は完全一致。キューを増やしても改善せず、キューに残らないDDS側の損失と整合する。同じ条件・プロセスのReliableは受信を継続できている。DDSの損失通知数とアプリケーション受信数は開始・終了タイミング等があるため厳密な全フレーム数の照合ではない。

両比較ともシステム全体のUDP `RcvbufErrors`, `InErrors`, `SndbufErrors` は増加0。計測プロセスの各UDPソケットの破棄数も0。IP再構成失敗は確認時0。コールバック本体の最大実行時間は標準時27.4 µs、64 MiB時16.0 µs。ただしこの時間はrclpy内部のデシリアライズ処理を含まない。

既存rqtはBest Effort購読であることを確認した。Best Effortだけが損失に弱い今回の結果はrqtの症状とも整合する。

## 容量の比較

- 画像1枚：640×480×3 = 921600バイト（900 KiB）。
- 標準のSHM：512 KiB（実ファイルは管理領域込み約537 KiB）。
- 比較用SHM：64 MiB（実ファイルも容量増加を確認）。

[Fast DDS 2.14公式資料](https://fast-dds.docs.eprosima.com/en/2.x/fastdds/transport/shared_memory/shared_memory.html)は、データサイズと同等またはそれ以下のセグメントでは送信中の上書きによる損失リスクを明記している。同じPCの双方でSHMが有効ならユーザーデータは通常SHM経由となるため、今回UDP破棄数が増えなかったこととも整合する。

これはSHM内部の上書き箇所をデバッガで直接観察したものではなく、同条件のQoS比較・容量変更による改善・公式仕様を組み合わせた判断。

## 適用した変更

`config/camera/fastdds_camera.xml` で標準と同じUDP＋SHMを定義し、SHMセグメントだけ64 MiBにする。ポートキュー容量や画像処理は変えない。`scripts/start_usb_camera.sh` がカメラプロセスにだけこの設定を読み込む。システム全体のsysctlや別プロジェクトのDDS設定は変更しない。以前のUDP限定・ループバック限定設定は使用しない。

生データ（Git管理外）：`log/camera_analysis/dds_*.csv`、`dds_queue_summary.json`、`dds_full_summary.json`、`dds_socket_samples.json`。増量比較は `shm64/`、カメラ側のみ増量した比較は `shm64_writer_only/`。

## カメラ側だけ増量した追加確認

受信側は標準DDS設定のまま30秒測定。3種類すべて807枚、DDS損失通知0。結果：

- best1: 807 frames, 26.91 fps, max gap 52.5 ms, >500ms 0
- best100: 807 frames, 26.91 fps, max gap 52.6 ms, >500ms 0
- reliable100: 807 frames, 26.94 fps, max gap 52.9 ms, >500ms 0

この構成では画像受信側へ特別なXML設定を追加する必要はなかった。長時間の表示や別環境での安定性は別途確認が必要。
