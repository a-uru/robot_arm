# ドライバ内の画像取得・publish計測

2026年11月6日。旧版v4l2_cameraに環境変数で有効になる計測を追加。通常起動ではCSVを書き出さない。

```bash
cd ~/robot_arm
mkdir -p log/camera_analysis
SO101_CAMERA_TIMING_CSV="$PWD/log/camera_analysis/driver_timing.csv" ./scripts/start_usb_camera.sh
```

起動後90秒の記録が終わるとCSVを閉じ、その後もカメラ配信は続く。画像は記録しない。計測中はCSVをバッファ付きで書き込み、フレームごとのコンソールログは出さない。

記録項目：

- `capture_ms`: V4L2から取得し、画像メモリにコピーしてバッファを返すまで。
- `dequeue_ms`: そのうち `VIDIOC_DQBUF` にかかった時間。
- `convert_ms`: RGBへの色変換など、取得後から変換完了まで。
- `prepare_ms`: メッセージヘッダー・CameraInfoの準備。
- `publish_ms`: ROSのpublish呼び出しが戻るまで。購読側への到達完了を意味しない。
- `sequence`: V4L2のフレーム番号。飛びがあるかを調べる。
- `buffer_age_ms`: 取得完了時の単調時計とV4L2バッファ時刻との差。フラグが単調時計を示す場合に解釈できる。
- `success`: 取得が成功したか。

結果はドライバCSVと、同時に購読した受信側CSVを比較して判断する。設定・画像サイズ・露出・中継処理は変更していない。

## 実測結果

ドライバ内90秒と、それに重なる受信側60秒を測定。既存のrqtも接続したまま。CSV出力以外の配信・カメラ設定は変更していない。

| ドライバ内処理 | 中央値 | 最大 |
| --- | --- | --- |
| 画像取得全体 | 34.64 ms | 292.70 ms |
| DQBUF待ち | 34.32 ms | 292.33 ms |
| 色変換 | 0.894 ms | 4.673 ms |
| メッセージ準備 | 0.005 ms | 0.162 ms |
| publish呼び出し | 0.304 ms | 4.093 ms |
| V4L2バッファ時刻から取得完了まで | 36.44 ms | 55.90 ms |

取得2231回すべて成功。V4L2 sequenceは0〜2230で欠落なし。取得・色変換・publishいずれも0.5秒以上の処理なし。取得待ちの最大292.70 msは起動直後。バッファ時刻は単調時計フラグを確認済み。

同時受信側は492枚、約8.31 fps。最大受信間隔1507.85 ms、0.5秒超の空白25回、1秒超8回。受信したメッセージのヘッダー時刻にも最大1508.05 msの飛びがあり、受信側にはその間の画像が届いていない。キュー深さ1・Best Effortでの追加購読の測定なので、受信できなかった画像が転送で失われたのか、ミドルウェアや購読側のキューで破棄されたのかまでは区別できない。

結論：今回再現した1秒程度の停止を画像取得・色変換・同期publish待ちでは説明できない。ドライバは継続してフレームを取得・publishしている一方、publish後〜購読側コールバック到達までの経路で画像が欠けている。次の対象はDDSの送受信・画像メッセージの転送・購読側キューやスケジューリング。これは撮影から画面表示までを直接測ったものではなく、rqt描画の遅延も別途残り得る。

撮影周期そのものは約33〜50 msの範囲で変わっているが、観測された1〜1.5秒の停止とは大きさが異なる。測定付近のUSB切断・UVCエラー記録なし。

生データ（Git管理外）：`log/camera_analysis/driver_timing.csv`、`driver_timing_summary.json`、`driver_receiver.csv`、`driver_receiver_summary.json`。
