# SO-101 の開始・停止時の衝撃と動作速度の調査

調査日：2026年10月28日。実機には動作指令を送らず、以前の記録、実行ログ、起動中のパラメーター読み取り、分離したROS領域での模擬試験を使用しました。

## 指令が実測位置へ飛ぶ原因

約120秒の記録では、角度指令と実測角度の配信頻度はどちらも約49.96 Hzでした。コントローラーのロード・アンロードが繰り返されている証拠はありません。確認できたのは、同じ `arm_controller` に対する軌道の受け付けとキャンセルです。

大きな終了時の指令変化は、MoveIt が実行時間超過を検出してキャンセルした直後に起きています。例：

| 記録開始から | 関節 | 約20 ms間の指令変化 | キャンセルからの時間 |
| --- | --- | --- | --- |
| 9.405秒 | elbow_flex | +3.23度 | 約19 ms |
| 38.746秒 | elbow_flex | +3.51度 | 約18 ms |
| 74.405秒 | shoulder_lift | −6.96度 | 約14 ms |
| 95.845秒 | elbow_flex | +4.72度 | 約10 ms |

肩の例では、指令が約−63.61度から約−70.58度へ飛び、変更後の値は直前の実測値と一致しました。MoveItログには `waitForExecution timed out`、`Stopping trajectory`、コントローラーログには `Got request to cancel goal` が記録されています。

JointTrajectoryController は通常、成功時には最後の軌道点を保持し、キャンセル時には実測位置を保持します。この違いが、残った追従誤差と同じ大きさの指令段差を作っています。機械的な遊びの有無はこの記録から断定できません。

開始時にも指令段差があります。新しい計画は実測位置から始まるため、前回の保持指令と実測位置に差が残っている場合、新しい軌道の開始点との間に段差ができます。`interpolate_from_desired_state` を変更するだけで、時刻0の明示的な開始点やキャンセル時の実測保持が解決するとは限りません。そのため、この設定を安易に変更してはいません。

## 適用した修正と限界

JTC の `constraints.goal_time` は2秒ですが、MoveItの実行監視にはその待機時間を含む余裕が必要です。`moveit_controllers.yaml` の両コントローラーに次を明記しました。

```yaml
allowed_execution_duration_scaling: 1.2
allowed_goal_duration_margin: 3.0
```

MoveItの待機上限は「軌道時間 × 1.2 + 3.0秒」です。コントローラーが2秒の目標到達待ちを行う前に、MoveItが早期キャンセルする状況を避けます。速度、可動範囲、目標誤差の許容値、キャンセルの保持動作は変更していません。

この修正は追従誤差自体をなくすものではありません。モーターが目標へ到達できず、JTCの到達許容誤差0.05 rad（約2.86度）を2秒以内に満たさなければ、依然として実行は失敗し得ます。開始時の残留誤差による段差も残る可能性があります。次に確認する対象は、姿勢・負荷ごとの静的追従誤差、モーターの位置制御設定、摩擦、たわみです。

## Scaling 1.0でも遅く感じる理由

稼働中のMoveItから読み取った上限は、各関節の速度0.5 rad/s、加速度0.5 rad/s²、ジャーク1.0 rad/s³でした。JTC自身の速度倍率も1.0です。RVizの倍率が1.0でも、速度上限は約28.65度/秒です。

記録から100 ms程度の差分で算出した速度絶対値の99パーセンタイルは次のとおりです。指令段差の影響を避けるため、0.8 rad/s以上の区間を除外しています。これは厳密なモーター速度限界の測定ではありません。

| 関節 | 指令 rad/s | 実測 rad/s |
| --- | --- | --- |
| shoulder_pan | 0.502 | 0.519 |
| shoulder_lift | 0.499 | 0.536 |
| elbow_flex | 0.438 | 0.476 |
| wrist_flex | 0.350 | 0.353 |
| wrist_roll | 0.497 | 0.491 |

少なくとも複数の関節で、指令は現在の速度上限付近に達しています。全体が倍率0.1に固定されている挙動ではありません。実測速度の小さな超過には、エンコーダー量子化、通信時刻の揺れ、実機追従が含まれます。

## 計画だけによる速度比較

実機と分離したROS領域で、他関節を0 radに保ち、shoulder_panを0から1 rad（約57.3度）へ動かす同じ目標を計画しました。動作の実行はしていません。

| 設定 | 速度・加速度倍率 | 計画時間長 | 計画上の最高速度 |
| --- | --- | --- | --- |
| 現在のRuckig設定 | 0.1 | 約21.010秒 | 0.05 rad/s |
| 現在のRuckig設定 | 1.0 | 約3.077秒 | 0.50 rad/s |
| Ruckigなし（比較のみ） | 1.0 | 約3.000秒 | 0.50 rad/s |
| ジャーク上限5.0（比較のみ） | 1.0 | 約3.010秒 | 0.50 rad/s |

この例ではRuckigの増分は約0.077秒で、遅さの主因ではありません。速度0.5 rad/sに達するまで、加速度0.5 rad/s²でも約1秒必要です。短い移動や複数関節を同期させる動作では、最高速度へ達する前に減速する場合もあります。

速度上限を上げれば計画は短くできますが、追従誤差が既にあるため、今回は上限を上げずに原因を切り分けました。モーター側の `Goal_Velocity` レジスターなどの実値は、稼働中のシリアル通信と競合しないよう直接読み取っていません。

## 模擬環境での修正検証

0.5秒の軌道に対し、到達後の整定に1.25秒必要な模擬コントローラーで比較しました。整定時間はJTCの2秒の待機内です。

- 旧設定相当（倍率1.2、余裕0.5秒）：約1.16秒でMoveItがタイムアウトし、キャンセルが発生しました。
- 修正設定（倍率1.2、余裕3.0秒）：約1.84秒で正常終了し、キャンセルは発生しませんでした。

この試験はMoveItの待機時間とキャンセルの有無を検証したもので、実機の追従誤差や衝撃の改善を検証したものではありません。数値結果は [比較試験結果](so101_motion_timing_results.json) に保存しています。

## 再起動後に確認すること

実機モードを一度停止して再起動し、軌道を再計画してください。停止中のアームは支え、実行中の設定変更・再起動は避けてください。

1. `waitForExecution timed out` が減るか。
2. 代わりに `goal_time_tolerance` のエラーが出るか。
3. 動作終了後の肩・肘の指令と実測角度の差が、待っても残るか。
4. 開始時と終了時の衝撃がそれぞれ変化するか。

終了許容誤差や位置情報を偽って成功扱いにする処理は追加していません。
