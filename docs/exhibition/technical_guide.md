## 1．30秒・90秒で説明する

### 30秒の説明

> 昨年は，人がコントローラーでロボットを操作していました．今年はカメラで四角い目印を見つけ，物体がどこにあるかを計算します．その位置までの動き方をパソコンで考え，開始の指示を出すと，つかんで運ぶところまで自動で行います．特に，小さい目印の認識の揺れを抑えることと，実際に動いた位置を確認してから次へ進むところを工夫しました．

### もう少し詳しい90秒の説明

> 台座と物体に，それぞれ違う番号のArUcoマーカーを付けています．カメラから見た2枚の位置関係と，台座に付けたマーカーの取付位置から，ロボットを基準とした物体の位置を求めます．
>
> 画像処理にはOpenCV，動き方の計画にはMoveIt 2，それぞれをつなぐ仕組みにはROS 2を使っています．
>
> 難しかったのは，画像上では小さいマーカーの角が少し揺れるだけで，計算した位置が大きく変わることと，モーターに指示した角度まで実物がぴったり動くとは限らないことです．そこで，角の位置を細かく求め，短い時間の複数画像で安定させました．また，各工程では現在の実測位置から計画し直し，把持位置に誤差が残った場合だけ，小さく補正する処理を入れています．

### 開発の進化を一言で

> 「人が見て動かす」から，「カメラで位置を求め，計画して動く」へ進めました．

完全な無人・連続運転ではない．現在は人の開始指示が必要で，対象や動作範囲にも条件がある．

## 2．何を使っているのか

| 名前 | 一言でいうと | このプロジェクトでの役割 |
|---|---|---|
| SO-101 | 小型のロボットアーム | ものをつかんで運ぶ機構 |
| STS3215 | 角度を指示できるサーボモーター | 各関節とグリッパーを動かし，現在角度を返す |
| USBカメラ | ロボットの「目」 | マーカーを含む画像を送る |
| ArUco | 番号を見分けられる四角い目印 | 台座と物体を区別し，位置・向きを求める手がかり |
| OpenCV | 画像処理の道具箱 | マーカー検出，角点精密化，位置・姿勢推定 |
| ROS 2 | ソフト同士をつなぐ共通の仕組み | 画像・座標・関節状態・動作要求をやり取りする |
| TF | 座標の関係を共有する仕組み | 台座，カメラ，マーカー，物体の関係を管理 |
| URDF | ロボットの寸法と関節の模型データ | 指先位置の計算や衝突判定に使う |
| MoveIt 2 | ロボットの動き方を計画するソフト | 関節の制限・衝突を考慮した軌道を作る |
| OMPL / RRTConnect | 道を探すアルゴリズム群／今回の計画器 | 関節角の組合せを探索する |
| ros2_control | 計画された動きと機体の間の制御基盤 | 時間に沿った角度指令と実測状態を扱う |
| RViz | 状態を立体的に表示する画面 | ロボット，座標軸，物体位置の確認 |

```text
USBカメラ
  ↓ 画像＋レンズの校正情報
OpenCV / ArUco
  ↓ マーカーの位置・向き
座標変換
  ↓ 台座から見た物体の位置
IK＋MoveIt 2
  ↓ 動かす関節角と時間付き軌道
ros2_control → motor_bridge → STS3215 → 実機
  ↑                                ↓
  └──────── 実測関節角 ────────────┘
```

**ROS 2が単独ですべてを判断するわけではない．** 検出・計画・実行を担当する複数のソフトをつなぐ基盤として使っている．

## 3．「工夫点は？」への答え方

### 最初に伝える3点

> 1つ目は，小さいマーカーでも位置が揺れにくいように，画像上の角の求め方を調整したことです．
>
> 2つ目は，カメラからの位置をそのまま使わず，台座と物体の2枚を同時に見て，ロボット基準の位置へ変換したことです．
>
> 3つ目は，計画通りに動いたと決めつけず，実測位置から計画し直し，必要な場合だけ把持位置を補正することです．

### 工夫の全体像

| 課題 | 採用した工夫 | 来場者向けの説明 |
|---|---|---|
| 小さいマーカーの角が不安定 | 角点のサブピクセル精密化と探索範囲の調整 | 「角をもっと細かく探します」 |
| 1枚ごとの画像ノイズ | 短い時間窓で角点の中央値を使う | 「数枚を見比べ，一瞬のぶれに引っ張られにくくします」 |
| 平面の向きが別の候補へ切り替わる | IPPEの候補と直前の回転を比較 | 「同じくらい画像に合う候補なら，向きが突然飛びにくい方を選びます」 |
| 違う時刻の観測を混ぜるとずれる | 画像とCameraInfoの同期，ID0・ID1の同時観測 | 「同じ瞬間の情報を組み合わせます」 |
| マーカー中心と必要な原点が違う | 取付・物体・TCPのオフセットを分離 | 「目印の位置と，つかみたい場所を区別します」 |
| 不安定な認識で動き始める | Enter時に直近の観測を検査 | 「位置が安定したときだけ開始します」 |
| 後半で行き止まりになる | 動かす前に全工程を仮計画 | 「最後まで行けそうか，先に調べます」 |
| 前工程で残った関節誤差 | 各工程直前に実測から再計画 | 「今いる場所から，次の道を考え直します」 |
| 把持点に少し届かない | 回数・移動量を制限した追加補正 | 「届かなかった分を，小さく調整します」 |
| 全工程を厳しくすると停止が増える | 把持とその他で到達許容値を分ける | 「つかむ場所と，運ぶ途中で必要な精度を分けます」 |
| 運ぶ途中に物体を引きずる | 上方の経由点を設ける | 「つかんだ後に，いったん上へ持ち上げます」 |
| 中断後に再開しづらい | Spaceで中断・待機位置復帰・開放 | 「指定の場所に戻ってから次を待ちます」 |
| 映像が遅れる・止まる | カメラとDDS転送を切り分けて調査 | 「撮影だけでなく，画像を運ぶ仕組みも調整しました」 |

### 自分で工夫した部分と，既存技術の区別

ArUco，IPPE，サブピクセル処理，MoveItなどのアルゴリズムを新しく発明したわけではない．本プロジェクトで工夫したのは，**小さいマーカーと実機の特性に合わせた設定・組合せ・同期・判定・再計画・補正の設計と検証**である．

「ライブラリを使っただけ？」と聞かれたら：

> 基本アルゴリズムは既存のものを使っています．ただし，組み合わせるだけでは，座標が合わない，映像が遅れる，指示通りに関節が動かないなどの問題がありました．どこで誤差が出ているかを記録して切り分け，実機で使えるように組み合わせ方を調整したことが開発の中心です．

## 4．ArUcoマーカー周りの処理

### 4.1 ArUcoとは

**来場者への短い答え**

> ロボットが見つけやすいように作られた，番号付きの四角い目印です．模様から番号と向きを見分け，四隅の見え方から位置と向きを計算します．

黒い外枠と内部の白黒模様を使う．今回は `DICT_4X4_50` という辞書のID0・ID1を使用する．「4×4」は内部の模様の構成で，黒い枠まで含めた物理サイズとは別の話である．

QRコードのような見た目だが，今回はURLなどの文章を読む用途ではない．IDは登録された模様の番号であり，番号の中に3D座標が書かれているわけではない．

### 4.2 なぜ普通のカメラで奥行きが分かるのか

> 目印の本当の大きさが分かっているからです．同じ大きさの目印が画像でどのくらい小さく，どんな形に見えるかを，カメラの校正情報と組み合わせて距離や向きを求めます．

このプロジェクトでは黒枠の外側から外側までを20mmとしている．白い余白は20mmに含めない．見た目の大きさだけでなく，4つの角の配置を使う．

印刷が縮小されて実物が19mmなのに20mmとして計算すると，距離の尺度にもずれが入る．マーカーの平面性や取付位置も重要である．**単眼カメラなので，既知サイズなどの手がかりなしに何でも奥行きを測れるわけではない．**

### 4.3 キャリブレーションは何をしているのか

> カメラの見え方の「ものさし」を作っています．レンズの拡大のしかたや画像のゆがみを調べ，画面上の位置を現実の位置へ結び付けます．

ここで得るのは主に焦点距離に相当する値，画像中心，レンズのゆがみである．今回のデータは `config/camera/ost.yaml` に保存し，CameraInfoとして配信する．

カメラ校正と，台座に貼ったマーカーの位置・向きを測ることは別の作業である．校正をし直しても，貼り付け位置の測り間違い，印刷サイズ，紙の反りまで自動修正されるわけではない．解像度・画角・ピントなどが変わると，校正条件が合わなくなることがある．

### 4.4 実際の処理の順番

1. カメラ画像と，その画像と同じ時刻のCameraInfoを受け取る．
2. 白黒模様を検出し，IDと4つの角を得る．
3. 角点をサブピクセル単位で精密化する．
4. 静止に近いときは，角点の短時間の中央値を使う．
5. 既知の20mmという寸法と校正値から，位置・姿勢の候補を計算する．
6. 候補の画像への合い方と，直前の向きとの連続性を確認する．
7. 再投影のずれを小さくする追加計算を行う．
8. 台座・マーカー・物体のオフセットを合成し，台座基準の物体位置を出す．

画像サイズ，CameraInfoの座標名，校正値，対応するゆがみモデルなども検査している．合わなければ，IDの検出だけできても3D姿勢は出さない．現在は最小辺が16画素未満のマーカーも3D推定の対象から外す．この16画素は精度保証の境界ではなく，最低限の品質判定である．

### 4.5 なぜ2枚のマーカーが必要なのか

| マーカー | 取付先 | 分かること |
|---|---|---|
| ID0 | ロボットの台座 | カメラとロボットの基準の関係 |
| ID1 | 運ぶ物体 | カメラと物体の関係 |

> カメラにとっての「物体の場所」を，ロボットにとっての「物体の場所」に直すためです．台座の目印が，2つの基準をつなぐ役割をします．

```text
台座の基準
  └─ ID0の取付位置・向きはあらかじめ測る
       └─ カメラから見たID0を使い，カメラの位置を求める
            └─ 同じ画像のID1から，物体の位置を台座基準へ直す
```

ID0とID1を別の時刻の画像から混ぜると，カメラや物体が動いている場合にずれが出る．そのため，**両方が同じ画像で検出されたときだけ，新しい相対物体位置を配信する**．ID0だけならカメラの位置関係は更新できるが，新しい物体位置は得られない．

後述の角点中央値には短い過去の履歴が含まれる．「同じ画像で検出を確認する」ことと，「値に時間的な遅れが一切ない」ことは同じではない．

### 4.6 原点とオフセットを分ける工夫

| 設定 | 意味 |
|---|---|
| `base_to_reference` | 台座原点からID0中心までの位置・向き |
| `marker_to_object` | ID1中心から，使いたい物体原点までの位置・向き |
| `grasp_offset_object_m` | 物体原点から，つかみたい点までの位置 |
| `tcp_offset_m` | グリッパーのモデル原点から，実際の把持中心までの位置 |

> 目印の中心と，つかむべき場所は同じとは限りません．その差を別々の設定として持たせています．

`TCP` は，ここでは指先の把持中心として扱う点である．各オフセットのXYZは，それぞれの親座標の軸で表す．例えばマーカーのX方向は，必ずしも台座のX方向ではない．向きまで含めて変換する必要がある．

カメラにも，画像用の「右・下・前」と，機体用の「前・左・上」という異なる軸の約束がある．`camera_link` と光学座標を分けることで，90度ずれたように見える混乱を避けている．

## 5．角点精密化と時間窓

### 5.1 角点精密化：どの角を細かくするのか

**来場者への短い答え**

> 四角い目印の角の場所を，1画素より細かい単位で探しています．ぼやけた境界の明るさの変化から，「本当の角はこの辺」と推定します．

画像は小さな画素の集まりである．最初の検出だけでは，角の位置が少しずれたり，隣の画素へ飛んだりする．OpenCVの `cornerSubPix` を使い，周囲の明るさの変化から角の位置を詰める．これが**サブピクセル精密化**である．カメラの画素数そのものを増やす処理ではない．

#### このプロジェクトでの工夫

撮影した画像では，20mmのマーカーが一辺28〜29画素ほどだった．このような小さいマーカーに対して，広すぎる範囲を使うと内部模様や別の境界の影響を受ける可能性がある．実画像を保存し，同じ画像で設定を比較して，探索範囲を小さくした．

現在の `corner_refinement_window: 3` は，OpenCVに渡す探索窓の**半径に相当する指定**である．単純に「3×3画素を使っている」という意味ではなく，中心を含む領域は概ね7×7画素になる．以前は5で，比較後に3を採用した．

`corner_refinement_accuracy: 0.001` は反復計算の終了条件の一つであり，「現実で0.001mmの精度」という意味ではない．

### 5.2 時間窓：なぜ何枚も使うのか

**来場者への短い答え**

> 1枚の画像だけだと小さなぶれに影響されるので，直近の数枚を見比べています．極端にずれた1枚に引っ張られにくい，中央値を使います．

例えば同じ角のX位置が `10.0，10.1，10.2，10.1，13.0` なら，中央値は `10.1` である．このように，突出した値の影響を抑える．

**現在は3D座標を後から平均するのではなく，画像上の4つの角のXY位置を，IDごとに最大5フレームで中央値化してから姿勢を計算する．**

#### 動いているものを無理に止めて見せない工夫

- 角が前フレームから，または履歴の最初から1.5画素を超えて動けば履歴をリセットする．
- 画像の時刻間隔が0.2秒を超えた場合や，時刻が戻った場合もリセットする．
- 今の画像に見えていないマーカーを，過去の値だけで検出済みにしない．

それでも小さな動きでは履歴が残る．30fpsなら5フレームの窓で約2フレーム，およそ67ms相当の遅れが生じ得る．**揺れを減らすことと，素早い動きに追いつくことにはトレードオフがある．**

### 5.3 「時間窓」はもう一つある

| 処理 | いつ使うか | 何をするか |
|---|---|---|
| 角点の時間窓 | マーカー姿勢を推定するとき | 最大5フレームの角の中央値を使う |
| 開始前の安定確認 | Enterを押したとき | 直近0.5秒程度の物体位置が十分新しく，安定しているか検査する |

後者では，少なくとも5つの異なる時刻の観測などが必要で，標準偏差や最大・最小の差も見る．**この開始判定は「最近の位置の平均を目標にする」処理ではない．安定していることを確認したうえで，最新の観測位置を固定する．**

また，開始後の「物体が動いたか」の判定は，現在の実装では新しい直近1観測と開始時の位置の比較である．複数観測の多数決に変えた実装ではないため，推定の一時的なずれでも停止する場合がある．

### 5.4 IPPEとLM：聞かれたら何と答えるか

**IPPE**

> 平面の四角がどこにあり，どちらを向いているかを計算する方法です．似た見え方になる候補が複数あるため，画像への合い方と，直前の向きを比較しています．

実装では `SOLVEPNP_IPPE_SQUARE` を使う．画像への再投影誤差が最良候補から0.3画素以内の候補について，直前の回転に近いものを選ぶ．過去の回転は0.5秒以内の履歴を使う．これは動作を予測するAIではなく，近い候補間での連続性の利用である．

**LMによる追加調整**

> 計算した3Dの四角をもう一度画像へ戻して，実際に見えた角と重なるよう微調整します．

`solvePnPRefineLM` を使い，再投影のずれが悪化しない場合に結果を採用する．ただし，画像上でよく重なることだけでは，現実の位置が正しいと保証できない．平面マーカーの向きの曖昧さや，校正・寸法の誤差は残り得る．

## 6．位置推定の揺れ・位置ずれ

### 揺れとずれは違う

| 状態 | 例 | 主な調べ方 |
|---|---|---|
| 揺れ | 止まっているのに推定値が毎回変わる | 角点，時間窓，姿勢候補，照明，画像サイズ |
| 位置の偏り | 毎回ほぼ同じ間違った場所を指す | 校正，実寸，取付オフセット，TCP，姿勢候補 |

> 時間窓で見た目を安定させても，間違った位置で安定してしまうことはあります．揺れの小ささと位置の正しさは別に確認します．

### 小さいマーカーで難しくなる理由

遠いマーカーは，画像上で少ない画素にしかならない．角が1画素未満ずれるだけでも，計算した距離や傾きには大きく影響する場合がある．さらにID0の向きの誤差は，離れた物体位置を台座基準へ直す際に大きな位置ずれとして現れる．

そのため，物体側ID1だけでなく，**基準になる台座側ID0の安定性も重要**である．画像の端での歪み，光の反射，紙の反り，ブレ，ピンぼけ，印刷サイズを確認する．

### 「どれくらい良くなった？」と聞かれたら

> 保存した同じ100枚の画像で，角点の探索窓と時間窓を比較しました．その画像列では，相対位置のX方向の標準偏差が約19.3mmから約3.8mmに減りました．ただし，これはその画像列でのばらつきで，実物に対する絶対誤差が3.8mmという意味ではありません．

完全静止や実物の真値は別装置で検証しておらず，搬送成功率を示す統計でもない．詳しい数値と条件は [実画像による比較](../aruco_accuracy_improvement.md) を参照．ポスターに載せていない内容なので，来場者への説明でも一般的な性能保証として扱わない．

改善の次の候補は，カメラを近づける，大きい基準マーカーや複数マーカーのBoardを使うこと．**台座と物体は独立に動くため，現在のID0とID1を一つの剛体Boardとして扱うことはできない．**

<a id="section-7"></a>

## 7．MoveIt・軌道計画・衝突判定

### 7.1 「どこへ」と「どう動く」を分ける

> カメラは行き先を求め，MoveItはそこへ行く動き方を考えます．

指先の位置から関節角を探すのが**逆運動学（IK）**である．本プロジェクトでは，URDFの寸法と関節角の制限を使い，指先の位置が目標へ合う候補を数値計算する．候補の衝突はMoveItのサービスで確認し，候補までの軌道をMoveItで計画する．

現在はアーム5軸での**位置中心の計画**で，好きな位置と好きな向きの6成分すべてを自由に満たせるわけではない．グリッパーの開閉は別の関節として扱う．

### 7.2 衝突判定とは

**来場者への短い答え**

> パソコンの中にロボットや障害物の模型を置き，その動き方で模型同士が重ならないか調べています．

ロボット自身のリンク同士，登録した障害物，持っている物体の形状を対象にする．MoveItの計画では，関節の可動範囲と衝突を確認する．

**重要：カメラに映った物体や来場者の手を，すべて自動で障害物として登録しているわけではない．** 現在のカメラ処理はマーカーによる位置推定であり，周囲全体の3D形状認識ではない．

現在の `table_enabled` は **false** で，机の衝突モデルは無効である．机を避ける保証を説明してはいけない．机のモデルは寸法・高さを測って有効にする必要がある．

### 7.3 把持した物体も模型に追加する

物体を持つと，手先だけでなく物体の分だけ接触しやすくなる．そこで把持後は，TCP中心の球をアームへ付けて計画する．標準半径は18mmで，物体原点と把持点の差があるとその分も含めて大きくする．20mm角程度の物体を想定した近似であり，任意サイズの物体形状を再構成しているわけではない．

グリッパーと把持物は接触するのが正常なので，指定した指のリンクとの接触を許可する．全体の衝突判定を切っているのではない．解放後は仮の球を削除し，古い物体模型が手先付近に残って次の計画を止めないようにしている．

### 7.4 全工程を事前計画し，実行時も計画し直す理由

**事前計画**は「つかんだ後に搬送先へ行けない」と分かるのを減らすための確認である．最後の待機位置への復帰まで，動き始める前に仮計画する．

**各工程の再計画**は，実機が仮計画の終点へ完全には届かない場合に備える．次は予想上の位置ではなく，現在の実測関節角から計画する．

これらを行っても，途中で環境や認識が変われば失敗する場合がある．事前計画の成功はサイクル全体の成功保証ではない．

### 7.5 「直接移動」や「上空を通る」は厳密な直線か

> 経由点を指定しているという意味です．いまは関節角の空間で道を探すので，厳密に真上へ一直線，その後水平一直線という保証ではありません．

OMPLの軌道は位置の経由点を結ぶ関節軌道である．必要なら，直線接近や姿勢・経路制約を別途設計する．計画が避けられるのは登録されたモデルであり，実際の全障害物ではない．

## 8．STS3215と関節の制御

### 8.1 STS3215とは

**来場者への短い答え**

> 「この角度へ動いて」と指示でき，現在の角度も読み取れるサーボモーターです．モーターの中にも，目標角度へ合わせるための制御が入っています．

角度センサー（エンコーダー）とモーター内部の制御を使う．複数のモーターをシリアル通信のバスにつなぎ，IDを指定して指令・状態取得する．この機体ではアーム5関節とグリッパーに使う．SO-101とSTS3215の関係は，[LeRobotのSO-101資料](https://huggingface.co/docs/lerobot/so101) でも説明されている．

### 8.2 誰がどこを制御しているのか

```text
MoveIt 2        ：関節をどの順番・時間で動かすか計画
ros2_control    ：時刻に合わせた目標角度を出す
motor_bridge    ：目標角度をサーボ通信へ変換し，角度を読む
STS3215内部     ：目標角度に近づくようモーターを制御
```

ブリッジは約50Hzのタイマーで位置の読取りと指令を行う．これはPC側の周期で，サーボ内部の制御周期が50Hzという意味ではない．現在のブリッジは主に位置を扱い，指先の接触力を制御しているわけではない．

### 8.3 PID・ゲイン・不感帯をやさしく説明する

| 言葉 | 説明 |
|---|---|
| Pゲイン | 目標とのずれに応じて，どのくらい強く戻そうとするか |
| Iゲイン | 長く残るずれを積み重ね，押し戻す働き |
| Dゲイン | 変化の速さに応じて動きを抑え，落ち着かせる働き |
| 不感帯 | ごく小さいずれには反応しない範囲 |

ゲインは大きければよいわけではない．上げすぎると振動・音・電流増加などにつながる可能性がある．Pだけを変えて比較するなど，一つずつ調べる．

これまでの初期記録は肩・肘ともP=16，I=0，D=32だった．P=20を試し，肘では20と24の静止比較も行ったが，その比較では明確に誤差が減らなかったため20へ戻した．**「最適なゲインへ調整し終えた」とは説明しない．** 現在の実値は電源・再起動の状況にもよるため，記録や読戻しで確認する．

### 8.4 モーターの負荷や電圧はどう見たか

> 指令角度と現在角度に加え，モーターが返す電圧・電流・温度・状態も記録して，単に遅いのか，ずれたまま止まっているのかを調べました．

診断は既存ブリッジの接続を使い，別のプログラムが同じシリアルポートを取り合わないようにした．設定変更時には元値を保存し，書き換えた値を読み戻す仕組みも用意した．

**Present_Loadは，物体の重さではない．** ST系資料ではモーターを駆動する出力デューティーとして説明されている．電流や出力値だけで，持っている物体の重量や把持力が正確に分かるわけではない．単位や状態ビットは [STサーボのレジスター資料](https://docs.waveshare.com/Memory_Map_Explanation/ST_Servo_Memory_Map_Explanation) を参照．

電源は利用者の申告では5V・4A．4Aは電源の供給能力で，常に4A流れているという意味ではない．過去の測定では約5.1〜5.2Vだった．型番には電圧違いがあるので，STS3215という名前だけで電源の適否を断定しない．

## 9．ゴール時の誤差と補正

### 9.1 「成功」と表示されたのに，なぜ止まるのか

**来場者への短い答え**

> モーターの角度が許容範囲に入ったことと，指先がつかむ場所へ届いたことは別だからです．このシステムでは両方を確認します．

| 判定 | 確認するもの | 単位 |
|---|---|---|
| 計画時の位置精度 | 計算上のTCPが目標へ合うか | m・mm |
| コントローラーの到達判定 | 各関節の指令角と実測角の差 | rad・度 |
| 実行後のTCP判定 | 実測関節角とモデルから計算した指先と，目標の距離 | m・mm |

肘の数度の誤差が，指先では1cm以上のずれになることがある．このため，コントローラーが `Goal reached` としても，その先のTCP検査で止まる場合がある．

現在の設定は，把持点のTCP到達許容値15mm，それ以外50mm．関節側は把持時0.065rad（約3.7度），それ以外0.10rad（約5.7度）．**許容値は，その誤差までなら進むという判定条件であり，実際の精度を良くする値ではない．**

### 9.2 「実測の指先」はどう測っているのか

関節のエンコーダー値とURDFから，TCPがあるはずの位置を計算する．これを**順運動学（FK）**という．

カメラで指先そのものを直接測っているわけではない．エンコーダーとモデルでは見えないたわみ，ホーンの緩み，寸法や関節原点の誤差，TCPオフセットの間違いは残り得る．

### 9.3 到達が遅いだけか，ずれが残るのか

目標が一定になった後も実測角が近づき続けるなら，遅れの可能性がある．目標も実測も一定で差が残るなら，単に待つだけでは改善しにくい．

これまでの記録では，肩や肘が目標に届かないまま一定になった例があり，失敗後にコントローラーが目標を現在位置へ変更することも分かった．**停止後だけを見ると元の誤差が消えたように見えるため，動作開始前から記録する必要がある**という切り分けも行った．

### 9.4 同じ目標へ再計画するだけでは不十分な理由

> 同じ場所へ行く同じ関節角が計算されると，モーターは同じところで止まってしまう可能性があります．そこで，実際に届かなかった方向を見て，指令する位置を少しずらします．

現在の把持補正は次の流れである．

1. 通常の速度設定で把持位置まで移動する．
2. 到達後のTCPが元の把持目標の許容内なら，追加待機なしで閉工程へ進む．
3. 許容外なら短く待って再確認し，残ったずれの一部を打ち消す指令位置を作る．
4. **最新の実測位置からMoveItで再計画し，衝突を確認して補正移動する．**
5. 補正後も，ずらした指令位置ではなく，**元の把持目標**に近づいたかを確認する．

例えば目標より右で止まったなら，次の指令を少し左へずらして，元の目標へ近づけようとする．実際の効き方は姿勢・負荷に依存するため，無制限に繰り返さない．

#### 補正に入れた上限

| 内容 | 現在の設定 |
|---|---:|
| 一度に打ち消す割合 | 残ったずれの70%を基準にする |
| 1回の補正変位 | 最大8mm |
| 元の把持目標からの指令位置のずれ | 最大25mm |
| 補正回数 | 最大3回 |
| 短い整定待ち | 0.15秒 |
| 補正軌道の関節の振れ | 計画開始位置から0.15rad以内 |
| 中止条件の一つ | 誤差が前回より1mmを超えて増える |

初回の通常経路を全体的に遅くしているわけではなく，必要なときだけ補正時間が加わる．ただしコントローラー自体が失敗した場合は，失敗を無視して補正を続けず停止する．

この補正は**関節の追従誤差への対応**で，カメラが間違って推定した物体位置を正しくする機能ではない．また，ゲインを調整することとも別である．

### 9.5 把持以外を5cm許容している理由

> つかむ点は細かく合わせますが，運ぶ途中は少しずれても作業が成り立つため，必要な精度を工程ごとに分けています．

ただし搬送先も50mmの許容対象なので，「指定位置にミリ単位で正確に置く」とは説明しない．グリッパーを閉じる角度を確認しても，実物を確実に持てたことまでは保証できない．

## 10．実際の動作と中断

### 通常の1サイクル

```text
グリッパーを開く（準備）
  → 物体の上方へ接近
  → 把持位置へ下降
  → 必要な場合だけ把持位置を補正
  → グリッパーを閉じる
  → 把持位置の真上でZ=0.15mの経由点へ
  → 搬送先へ移動
  → グリッパーを開く
  → 待機位置へ戻る
```

Z=0.15mは**台座基準で高さ15cm**であり，現在位置から15cm持ち上げるという意味ではない．把持位置がすでにそれより高ければ高さを維持する．経由点にも把持以外の到達許容値が適用されるので，厳密に高さ15cmを通過する保証ではない．

待機位置は `[0.0, -0.2, 0.2]` mで，搬送先とは独立した設定．搬送先は `place_xyz_m` で変更する．

### Spaceを押したとき

実行中アクションのキャンセルと終了を確認し，現在位置から待機位置への道を計画する．物体を持っている可能性があるときは，待機位置に着くまでグリッパーを開かず，到達後に開放して次のEnterを待つ．戻れなかった場合は，自動開放せず停止する．

Spaceはlaunchを起動したターミナルで受け付ける．復帰途中に再度Spaceを押すと復帰も停止する．**Spaceは自動で戻る動作を含むソフトウェア操作であり，ハードウェア非常停止ではない．**

### 展示中に止まったときの説明

> 位置の認識や到達状態が条件に入らなかったため，次の動作へ進まず止まっています．動かし続けるより，確認してから進める設計にしています．

続けて「どの判定か」を確認する．

| 表示の例 | 意味 |
|---|---|
| `No fresh ... pose` | 両マーカーの新しい観測がない |
| `moving/unstable` | 開始前の推定位置が安定しない |
| `object estimate shifted` | 開始後の推定位置が15mmを超えて変化した |
| `outside workspace` | 目標が設定した作業範囲外 |
| `CheckStartStateCollision` | 計画開始時のモデルに衝突がある |
| `GOAL_TOLERANCE_VIOLATED` | コントローラーの関節到達条件を満たさない |
| `TCP missed target` | 指先位置の到達条件を満たさない |
| `correction exhausted / worsened` | 補正回数を使い切った／誤差が増えた |

ログの停止理由を確認せず，単に許容値を広げることを「精度改善」として説明しない．

## 11．よくある質問

### Q．AIを使っていますか

> 現在の展示は，目印を使った画像処理と幾何計算，軌道計画が中心です．生成AIやVLAで動作を決めているわけではありません．今後はVLAを使い，より多様な物体と作業へ対応したいと考えています．

### Q．VLAとは何ですか

> Vision・Language・Actionの略で，画像や言葉の指示を，ロボットの行動につなげるモデルです．今後の方針として，目印に頼る現在の方式から，多様な物体を扱う方向へ広げたいと考えています．

VLAを入れればどんな物体でもすぐ扱えるとは限らない．機体・データ・タスクに合う学習や検証が必要で，現時点では今後の計画である．

### Q．なぜマーカーを付けるのですか

> ものの色や形を自由に認識する問題より，位置を求める仕組みを作りやすいからです．まずは分かりやすい目印で，認識から実行までを一通りつなぎました．

### Q．何でもつかめますか

> 現在はマーカーを付けた対象で，寸法・重さ・置き方・アームの届く範囲などの条件があります．物体の形から最適なつかみ方を自動生成する仕組みではありません．

### Q．普通のカメラですか．深度カメラですか

> 現在は単眼USBカメラです．マーカーの既知の大きさを使って位置と向きを計算しています．画面の全画素の奥行きを測っているわけではありません．

### Q．カメラが動いても使えますか

> 台座側のID0と物体側のID1を同時に観測できれば，カメラの位置関係を更新して相対位置を求める構成です．ただし，動きによるブレや遮蔽，推定の誤差までなくなるわけではありません．

### Q．手や人を自動で避けますか

> 現在は，カメラから人や障害物の3D形状を自動登録する仕組みはありません．衝突判定は登録したモデルが対象です．展示中はスタッフが見守り，動作範囲へ入らない形で運用します．

### Q．どうして止まっている目印の座標が揺れるのですか

> 小さい画像上の四隅から3Dの向きを計算しているので，わずかな画素の変化が大きな位置の変化になる場合があるためです．角点精密化と短い時間窓で影響を抑えています．

### Q．マーカーを何枚も増やせばよいのですか

> 同じ台座に，配置が分かった複数のマーカーを固定してまとめて計算するBoard方式は改善候補です．ただし，同じIDの予備を何枚も同時に見せるだけでは，どれを基準にするか曖昧になります．現在はID0とID1をそれぞれ1枚ずつ使う想定です．

### Q．去年との違いはどこですか

> 去年は人がコントローラーで動かしていました．今年は開始を指示すると，カメラで求めた位置を基に，計画・把持・搬送・待機位置復帰までを実行します．認識と動作をつないだことが大きな違いです．

### Q．一番苦労したところは何ですか

> 認識，座標変換，モーターの誤差が同じ「位置ずれ」に見えることです．画像の揺れなのか，基準座標の設定なのか，関節が届いていないのかを，記録して分けて調べました．

### Q．独自性はどこですか

> 各ライブラリの新発明ではなく，小型アームに合わせて，目印の安定化，座標の整合，実測からの再計画，把持位置補正までを組み合わせた実装上の工夫です．性能の新規性を研究成果として主張するには，比較実験などがさらに必要です．
